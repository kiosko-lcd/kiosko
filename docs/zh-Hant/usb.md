# 透過 USB 連接面板

**USB** 連線（`"device": { "driver": "usb" }`）讓 Kiosko 透過 libusb 自己和 Thermalright LY 系列面板（Trofeo Vision 9.16 及同系列；USB `0416:5408` 和 `0416:5409`）通訊，不需要 Python，也不需要 `trcc serve`。

```json
"device": { "driver": "usb", "serial": "202592047DAE" }
```

- `serial`：USB 序號。**有多個相同的面板時，序號是唯一能區分它們的依據**，所以請務必填寫。找不到指定序號的面板時，Kiosko 會一直等它出現，絕不會改用另一個面板（若搶走另一個程式正在使用的相同面板，會讓那個面板變成黑畫面）。留空：使用第一個找到的面板。
- `keepalive`：畫面沒有變化時，重新傳送同一個影格的間隔秒數（預設 1）。最後一個影格送出後 2–3 秒，韌體就會重新顯示出廠標誌。

`kiosko doctor` 會列出 libusb 看得到的面板及其序號；在編輯器的 **螢幕 → 新增螢幕 → 偵測面板** 中也能直接選擇它們。

影格一律以 JPEG 格式傳送。韌體最多只接受約 511 871 位元組，超過的影格會被**默默丟棄**；Kiosko 會讀取面板的確認回應，並在該螢幕的狀態中告訴你（「面板丟棄了一個 … KB 的影格：請調低 JPEG 品質」）。

## 拔除的面板會讓它的螢幕暫停（在位偵測）

面板不在時，它的螢幕照樣合成頁面、繪製小工具、編碼畫面，白白耗費 CPU。所以 Kiosko 會**暫停面板不在的螢幕**：不為它合成、繪製或編碼任何東西，它的過場動畫、動畫和警報都會等待，只有它在顯示的資料來源和擷取也會停止。之後會以很低的開銷重新尋找（2 秒、4 秒、8 秒……最長每 30 秒一次；有 USB 熱插拔事件時立即尋找：Linux 上用 `/dev/bus/usb` 的 inotify，其他系統用 libusb 的熱插拔事件），面板一回來，螢幕就**用一張全新的完整畫面繼續**。編輯器會顯示「面板未連接 · 已暫停（節省 CPU）」，`kiosko doctor` 會顯示每個影格檔案螢幕的在位情況。你關掉的螢幕仍然保持關閉：在位偵測不是螢幕的開關。

在獨立執行緒裡繪製的螢幕暫停滿一分鐘後，還會交還這個執行緒（執行緒占用的記憶體：外掛、字型、圖片和已繪製的圖塊，幾十 MB）；面板回來時再分配一個新執行緒，從頭繪製完整的一幀。

- **USB** 連線：自動。沒有插上帶有該 `serial` 的 LY 面板（沒填序號時：一個都沒有）就算不在。只查看，不開啟裝置。
- **遠端螢幕**：自動。離線（沒有工作階段、沒有 mDNS 廣播）或未配對都算不在；它一廣播就立即恢復。
- **影格檔案**：Kiosko 看不到傳送程式驅動的面板，需要用 `presence` 告訴它怎麼判斷（不設定時螢幕和以前一樣一直繪製）：

```json
"device": {
  "driver": "file",
  "dir": "$XDG_RUNTIME_DIR/kiosko/left",
  "presence": {
    "usb": { "vendorId": "0416", "productId": "5408", "serial": "202592047DAE" },
    "heartbeat": { "path": ".heartbeat", "maxAgeMs": 5000 }
  }
}
```

- `usb`：插上了具有這個廠商 ID、產品 ID（和序號）的 USB 裝置。唯讀：Linux 上從 sysfs 讀取，完全不開啟裝置；其他系統上 libusb 會短暫開啟裝置讀取序號（每次插上只讀一次），絕不佔用它。傳送程式繼續使用面板，不受打擾。
- `heartbeat`：傳送程式驅動面板期間會不斷更新的檔案；檔案不存在或超過 `maxAgeMs`（預設 5000）就算不在。相對路徑位於 `dir` 之內。`contrib/usb-sender` 裡的傳送程式在面板連接期間，每秒更新一次它正在顯示的資料夾裡的 `.heartbeat`。
- `command`：`{ "argv": ["lsusb", "-d", "0416:5408"], "everyMs": 30000 }`：面板在時以 0 結束的程式（不經過 shell）；每 `everyMs` 執行一次（最少 5 秒），超過 10 秒會被終止。匯入設定時，它會和其他會執行程式的值一樣列出來供你檢查。

設定了多種偵測時：**任何一種**說不在就算不在。無法判斷的偵測（沒有 libusb、讀不到序號的同款面板）會說「未知」，這樣的螢幕照常繪製。

在編輯器中：**螢幕 → （該螢幕）→ 影格檔案 → 面板拔除時暫停**；**偵測序號** 會以唯讀方式列出該 VID:PID 的裝置及其序號，並標出哪個螢幕已經在用。

**相同的面板必須填序號。** 所有 Trofeo Vision 面板都回報 `0416:5408`。沒有 `serial` 時，Kiosko 只知道插著*某一個*面板，永遠不知道*是哪一個*，所以只有在**一個都沒插**時才會暫停螢幕。三個拔掉兩個、又沒填序號時，什麼都不會暫停，這是刻意的：如果暫停了一個其實還在的面板，它的畫面就會凍結。`kiosko doctor` 會列出序號（也可以用 `lsusb -v -d 0416:5408 | grep iSerial`）。

### 使用 trcc 傳送程式（`contrib/usb-sender`）

每個傳送程式依序號驅動一個面板，顯示某個資料夾裡的 `frame.jpg`。給每個影格檔案螢幕設定*它自己的*傳送程式的在位偵測：

- 傳送程式設定裡沒有 `wheel` 時，兩種都可以：`usb` 加上該傳送程式的 `serial`，不需要傳送程式配合；`heartbeat` 還能發現傳送程式沒在執行。
- **有 `wheel`**（幾個面板每隔幾個小時輪流顯示各個資料夾）時，一個面板顯示的資料夾會變，它的序號無法說明它在顯示哪個螢幕：只用 **`heartbeat`**（`{ "path": ".heartbeat" }`）。傳送程式更新的是它*此刻*顯示的資料夾的心跳檔案，所以只有正被某個已連接面板顯示的螢幕才會繪製；輪換時，新資料夾的心跳會在一秒內更新，它的螢幕隨即恢復。

心跳需要更新後的 `kiosko-sender.py`（除非它的設定寫了 `"heartbeat": false`，否則會更新 `.heartbeat`）。舊版傳送程式從不更新它，螢幕就會一直暫停：請先更新傳送程式。

## 各作業系統需要做什麼

**Linux。** 你的使用者帳號必須有權限開啟這個裝置。如果 `kiosko doctor` 顯示 `(unreadable)` 或存取錯誤，請加入一條 udev 規則，然後重新插拔面板：

```
# /etc/udev/rules.d/99-kiosko-lcd.rules
SUBSYSTEM=="usb", ENV{DEVTYPE}=="usb_device", ATTR{idVendor}=="0416", ATTR{idProduct}=="540[89]", TAG+="uaccess"
```

（接著執行 `sudo udevadm control --reload && sudo udevadm trigger`。）Kiosko 使用面板期間會暫時卸離核心驅動程式，停止時再交還。兩個程式不能同時使用同一個面板：要交給 Kiosko 的面板，請先停止正在驅動它的 `trcc serve` 或 `kiosko-sender`。

**Windows。** libusb 只看得到使用 **WinUSB** 驅動程式的裝置，所以每個面板都要先用免費工具 [Zadig](https://zadig.akeo.ie/) 換上 WinUSB 驅動程式。這件事每個面板只需做一次：

1. 下載並執行 Zadig。它需要系統管理員權限，跳出「使用者帳戶控制」視窗時請按 **是**。
2. 在選單中勾選 **Options → List All Devices**（列出所有裝置），否則清單裡可能看不到面板。
3. 從下拉式清單中選擇面板。辨認的方法是看下方的 USB ID：`0416` 和 `5408`（或 `5409`）。**請小心不要選錯**，選到滑鼠、鍵盤或其他裝置會讓它們無法正常使用。
4. 在箭頭右邊的驅動程式欄位選擇 **WinUSB**。
5. 按 **Replace Driver**（取代驅動程式），等待完成。

換上 WinUSB 之後，Thermalright 官方的 TRCC 軟體就看不到這個面板了；如果需要改回來，可以在「裝置管理員」中還原原本的驅動程式。沒有安裝 WinUSB 時，`kiosko doctor` 會顯示 `LIBUSB_ERROR_NOT_SUPPORTED`。

**macOS。** 不需要安裝任何東西。

原生模組（`usb`）是**選用**的相依套件，附有 Linux、macOS 和 Windows 的預先編譯版本；即使它無法載入，Kiosko 的其他功能仍照常運作，這個連線方式也會告訴你原因。

## 開發狀態

本功能依據 [thermalright-trcc-linux](https://github.com/Lexonight1/thermalright-trcc-linux) 9.12 所實作的通訊協定撰寫：對 `packages/usb-ly` 中的 22 個測試影格（由 `trcc` 本身產生），每個影格送出的位元組資料流與 `trcc` 完全相同，其餘部分則以模擬的韌體進行測試。**目前還沒有在真正的面板上執行過**，也還沒在 macOS 或 Windows 上執行過：請把它當成實驗性功能，並保留 `trcc serve` 或畫面檔案傳送程式作為備案。
